# AIGC-GameFlow 高负载与削峰加固 PRD V3

> 版本：V3.0
> 状态：核心范围已实施
> 核心目标：在不增加新业务和重型中间件的前提下，让入口限流、查询轮询和队列削峰形成真正的过载保护闭环。

## 1. 背景

V2 已具备幂等提交、原子扣费、Redis 限流、RabbitMQ 异步执行、状态 CAS、重试和 DLQ。但代码审计发现四个高负载风险：

1. 幂等数据库查询发生在 Redis 限流之前，无效流量仍会先访问 MySQL。
2. Web 控制台每两秒轮询任务列表，列表查询直接访问 MySQL，未利用单任务 Redis 缓存。
3. RabbitMQ 主队列没有积压阈值，持续流入大于消费能力时可能无限占用磁盘。
4. 连接池参数依赖框架默认值，压测环境不可复现。

本版本只修复以上控制面问题，不引入微服务、Kafka、Sentinel、注册中心或分库分表。

## 2. 用户场景

游戏活动开启后，大量用户在短时间提交海报生成任务。系统需要：

- 在数据库之前拒绝超过配额的请求。
- 正常请求快速返回任务编号，慢速图片生成留在 RabbitMQ 中执行。
- 在线用户轮询任务状态时优先读取 Redis，不形成 MySQL 查询洪峰。
- 队列积压超过安全阈值后暂停接收新任务，向客户端返回明确的可重试响应。
- 流量下降、队列恢复到安全水位后自动恢复接单。

## 3. 范围

### 3.1 本期必须实现

1. Redis 幂等结果缓存，命中时不访问 MySQL。
2. 未命中幂等缓存时，先执行 Redis Lua 限流，再查询数据库。
3. RabbitMQ 主队列与重试队列积压采样。
4. 超过积压阈值返回 HTTP 503 和 `Retry-After`。
5. 前端只在首次加载时查询任务列表；运行中任务通过最多 20 条的批量状态接口轮询。
6. Tomcat、HikariCP、Redis 连接池参数显式化并支持环境变量覆盖。
7. 多用户压测账号准备脚本与 JMeter CSV Token 输入。
8. 记录正式压测所需的环境、RPS、P95、P99、错误率和队列峰值。

### 3.2 明确不做

- Transactional Outbox、RabbitMQ 集群和 MySQL 主从。
- 自动扩缩容、Kubernetes、Prometheus 和 Grafana。
- WebSocket/SSE；当前阶段使用低频 Redis 状态轮询。
- 分库分表以及为虚构数据进行的过度优化。
- 对真实付费 Provider 进行压力测试。

## 4. 核心流程

```text
提交请求
-> Redis幂等结果缓存命中：直接返回原taskUuid
-> Redis Lua用户级/全局限流
-> RabbitMQ积压保护
-> Redis短锁
-> MySQL查询最终幂等记录
-> 本地事务原子扣费并创建任务
-> RabbitMQ Publisher Confirm
-> 写入Redis幂等结果缓存
-> 返回taskUuid
```

状态查询流程：

```text
首次进入页面 -> MySQL查询最近20条任务
存在运行中任务 -> 每2秒批量查询最多20个taskUuid
批量查询 -> Redis MGET；未命中的任务一次性批量回源MySQL
所有任务结束 -> 停止自动轮询
```

## 5. Redis 设计

### 5.1 幂等结果缓存

```text
Key: idempotency:result:{userId}:{sha256(idempotencyKey)}
Value: {requestHash}:{taskUuid}
TTL: 24小时
```

请求哈希不一致返回 HTTP 409。Redis 只是快速路径，MySQL 唯一索引仍是最终防线。

### 5.2 限流

- 用户默认：5 次/秒。
- 全局默认：300 次/秒。
- 超限返回 HTTP 429、`Retry-After: 1`。
- 限流必须发生在常规 MySQL 查询之前。

## 6. 队列积压保护

应用每秒通过 RabbitMQ 被动声明读取：

- `generation.execute.q` 可消费消息数。
- `generation.retry.q` 可消费消息数。

默认规则：

- 总积压小于 5,000：正常接收任务。
- 总积压达到或超过 5,000：拒绝新任务，返回 HTTP 503。
- RabbitMQ 状态连续不可读取时：失败关闭，拒绝新任务，避免数据库继续写入无法投递的任务。
- 已存在的幂等请求仍优先从 Redis 返回，不重复创建任务。

响应示例：

```http
HTTP/1.1 503 Service Unavailable
Retry-After: 5
```

## 7. 资源池基线

每个 App 默认值：

| 资源 | 默认值 |
| --- | ---: |
| Tomcat 最大线程 | 200 |
| Tomcat accept-count | 500 |
| Hikari 最大连接数 | 20 |
| Hikari 最小空闲 | 5 |
| Redis 最大连接数 | 32 |
| RabbitMQ Worker | 4～16 |
| RabbitMQ prefetch | 20 |

这些值是可复现的压测起点，不是性能结论。最终值必须通过连接池等待时间、数据库 CPU 和队列吞吐调整。

## 8. 验收标准

### 8.1 自动化正确性

- 幂等缓存命中时不执行限流和 MySQL 查询。
- 常规新请求先限流，再执行数据库查询。
- 队列超过阈值时不扣费、不创建任务，返回 503。
- 相同幂等键并发提交仍只创建一条任务并只扣费一次。
- 前端轮询运行中任务时不重复调用任务列表接口。

### 8.2 压测目标

以下为目标，不是当前实测结果：

| 场景 | 目标 |
| --- | --- |
| 提交接口 | 300 个成功接纳请求/秒持续 60 秒 |
| 正常负载延迟 | P95 < 200ms，P99 < 500ms |
| 超额流量 | 稳定返回 429，不出现大量 500 |
| 积压保护 | 达到阈值后 2 秒内开始返回 503 |
| 幂等风暴 | 相同 Key 100 并发只创建 1 条任务 |
| 状态轮询 | Redis 命中路径不访问 MySQL |

## 9. 压测口径

正式报告必须同时写清：

- CPU、内存、JDK、Docker 和数据库配置。
- App 实例数、HTTP 线程池和连接池大小。
- 测试用户数量及每个用户余额。
- 成功 RPS、429/503 数量、P95、P99、错误率。
- RabbitMQ 主队列、重试队列和 DLQ 峰值。
- 图片 Worker 平均耗时与完成吞吐。

“300 RPS”表示入口成功接纳速度；“最大 32 Worker”表示执行面并行度，两者不能混为同一个并发数字。

## 10. 面试口径

> 系统把入口控制面和图片执行面分开度量。入口通过 Redis Lua 限制成功接纳速率，并在 RabbitMQ 积压达到阈值时返回 503；执行面通过有限 Worker 并行度保护 GPU 或第三方 Provider。幂等缓存将重复请求挡在数据库之前，MySQL 唯一约束和状态 CAS负责最终正确性。前端只轮询 Redis 命中的任务详情，避免在线用户形成列表查询洪峰。
